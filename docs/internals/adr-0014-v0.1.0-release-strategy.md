# ADR-0014: v0.1.0 release strategy

**Status**: Accepted
**Date**: 2026-06-06
**Milestone**: M1.7 — first public release
**Spec**: [`docs/superpowers/specs/2026-06-06-m1.7-release-design.md`](../superpowers/specs/2026-06-06-m1.7-release-design.md)
**Plan**: [`docs/superpowers/plans/2026-06-06-m1.7-release.md`](../superpowers/plans/2026-06-06-m1.7-release.md) *(written next, after this ADR)*

## Context

After 23 commits of feature work (F1.x / F2 / B1 / C1–C2 / D1–D3),
`agentprof` reaches 809 passing tests, complete docs, and
`Cargo.toml.version = "0.1.0"` but has never been released. M1.7
turns "private local checkout" into "publicly installable artifact."

Two hard blockers gate the release:
1. `full-review-workspace-2-release-yml-stub` — `release.yml` is a
   stub draft-release; README already advertises
   `cargo install agentprof` (cargo-dist) but nothing implements it
2. `full-review-workspace-3-actions-sha-pin` — every `uses: org/repo@vX`
   in CI workflows is tag-pinned, not SHA-pinned (OpenSSF Scorecard
   medium-severity supply-chain finding)

The release work is more than CI hardening — it requires committing to a
distribution model (crates.io vs GitHub-only), supported platform set,
installer convention, signing posture, CHANGELOG flow, and release
choreography. This ADR records those decisions so future maintainers
know **why** the wiring looks the way it does.

## Decisions

(Each row maps 1:1 to a decision in the M1.7 spec §2. Re-opening a
decision requires editing this ADR or recording a new ADR that
explicitly supersedes the affected D-row.)

- **D-1** **No crates.io publish for v0.1.0.** YAGNI — the workspace
  has 5 crates with a large pre-stable API surface (4 of which are
  internal). `cargo install --git` covers source-build users; the
  cargo-dist installer covers binary users. Opening crates.io publish
  later is non-breaking (just remove `publish = false` on whichever
  crates we want, add a `publish-jobs = ["homebrew", "cargo"]` line
  to `dist-workspace.toml`, and bump the version). Conservatively
  not committing to that surface yet means we can change lib API
  semantics in v0.x without breaking external consumers.

- **D-2** **GitHub repo slug** = `github.com/verdenmax/agentprof`.
  Already set in `Cargo.toml.repository` + `homepage` during M1.0.
  All README + ADR + installer URLs assume this slug. If `agentprof`
  the GitHub org or repo name is taken at registration time, fall back
  to `agentprof/agentprof-cli` (matches the bin crate name); in that
  case the spec §10 risk row + this ADR D-2 + Cargo.toml + README +
  installer URL all need a coordinated update **before** pushing the
  v0.1.0 tag (the URLs are baked into installer.sh template). The
  spec's Stage-2 step 5 includes a "confirm repo slug" gate.

- **D-3** **4 lib crates set `publish = false`; `agentprof-cli` omits
  the field.** Defence-in-depth: even if a maintainer accidentally
  runs `cargo publish` from a `crates/agentprof-core/` checkout, the
  publish fails with a clear error. cli omits the field (rather than
  `publish = true`) to leave the option open without changing existing
  behaviour. Rejected alternative: set `publish = false` on cli too —
  would force a code change to ever open crates.io publish, which is
  the opposite of "low-friction future expansion."

- **D-4** **Primary install** = one-line cargo-dist shell installer:
  `curl -fsSL https://github.com/verdenmax/agentprof/releases/latest/download/agentprof-cli-installer.sh | sh`.
  Rationale: zero Rust toolchain required for end users; ratio of
  download time vs source-build (cargo install --git takes ~3 minutes
  on a typical M1 Mac, the installer takes ~5 seconds + ~20MB download);
  pinning specific versions is supported (`/download/v0.1.0/` replaces
  `/latest/`); cargo-dist generates and maintains it for free. Two
  source-based fallbacks (`cargo install --git`, `cargo install --path`)
  preserved in README for Rust developers who prefer not to trust a
  shell pipe.

- **D-5** **Build matrix = 4 platforms** — `x86_64-unknown-linux-gnu`,
  `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`.
  This is cargo-dist's default-recommended set. **Windows excluded** for
  v0.1.0: ratatui has known Windows-terminal quirks (different ANSI
  handling, alt-screen behaviour) that would require a Windows TUI
  test pass we don't currently have; the project's target audience
  (AI agent CLI users) skews macOS/Linux. v0.2+ can add
  `x86_64-pc-windows-msvc` once a Windows tester is available.

- **D-6** **SHA-pin all immutable-tag actions; rolling refs
  (`@stable` / `@master`) intentionally remain tag-pinned with a
  comment.** OpenSSF Scorecard recommends SHA-pinning to defend against
  malicious tag-rewriting at upstream actions; per-reference comment
  (e.g. `actions/checkout@<40-sha>  # v4.2.2`) preserves human
  readability. Rolling refs are deliberately not pinned — `dtolnay/rust-toolchain@stable`
  is rolling **by design** (each CI run picks up the current stable
  Rust toolchain); pinning it would freeze the toolchain at one commit
  forever and silently miss MSRV bumps. A code comment at each rolling
  ref documents the intent so future SHA-pin audits don't "fix" them.
  Dependabot (configured per §6.5) auto-bumps the immutable SHA + the
  trailing `# vX.Y.Z` comment together.

- **D-7** **No signing — neither tag nor binary.** cargo-dist
  auto-generates SHA-256 checksums (`SHA256SUMS` file or per-file
  `.sha256` siblings) that verify download integrity. GPG signing
  (tag or binary) would require GPG key management, secure key storage
  in GitHub secrets, key rotation policy, and a way for users to
  verify keys out-of-band — too much overhead for v0.1.0. Future
  alternatives if user demand surfaces: sigstore cosign (no key
  management, OIDC-based), minisign (small per-binary keys). Adding
  signing later is non-breaking (just enables verification, doesn't
  invalidate previous unsigned releases).

- **D-8** **First public version = `v0.1.0`.** Matches existing
  `Cargo.toml.workspace.package.version`. SemVer 0.x signals "API
  not stable" — honest given C1 just shipped a BREAKING JSON change
  (`AggregateReport.since` → `Option<Duration>`) within the last week.
  Rejected `v0.0.1` ("pre-1.0 of pre-1.0"): the project is
  feature-complete enough for the M1.x roadmap that calling it
  pre-pre-release would understate it. Rejected `v0.1.0-rc.1`
  intermediate: adds a release rehearsal pass but doesn't catch
  meaningfully different failure modes than the spec's Stage-2 abort
  path (tag delete + re-tag).

- **D-9** **CHANGELOG follows standard Keep-a-Changelog cutover** at
  tag time: `[Unreleased]` body → `[0.1.0] - YYYY-MM-DD` + new empty
  `[Unreleased]` above. Link references appended at the bottom
  (`[0.1.0]: .../releases/tag/v0.1.0`, `[Unreleased]:
  .../compare/v0.1.0...HEAD`). Single `chore(release): v0.1.0` commit
  performs the cutover; this commit is also the one the v0.1.0 tag
  points at. Rejected alternative: keep everything in `[Unreleased]`
  and rely on GitHub's auto-generated release notes — that creates
  two sources of truth for "what changed in this release" which
  inevitably diverge.

- **D-10** **Two-stage release.** Stage 1: 10 prep commits land on
  local `main`; full local gate (fmt + clippy + test + rustdoc +
  `cargo dist plan`) must pass. Stage 2: maintainer creates GitHub
  repo, pushes commits, tags + pushes; `release.yml` fires, builds
  4 platforms, uploads to GitHub Release; maintainer manually tests
  the installer URL on their machine + runs `agentprof --version` to
  confirm the release works end-to-end. If ANY Stage-2 gate fails,
  abort entirely (delete tag + delete release + fix + re-tag) rather
  than patch-forward from a known-broken v0.1.0. Rejected alternative:
  three-stage with `v0.1.0-rc.1` rehearsal — doesn't catch different
  failure modes than the abort path, costs an extra cycle.

- **D-11** **`cargo dist init` generates yml + manual one-time SHA-pin**;
  no xtask automation. The first cargo-dist run produces a `release.yml`
  referencing cargo-dist's preferred actions (in 0.21.x: `actions/checkout`,
  `actions/upload-artifact`, `actions/download-artifact`,
  `softprops/action-gh-release`). All immutable-tag refs in the
  generated yml get manually SHA-pinned in the same commit. **Why
  not write a `xtask sha-pin-release-yml` automation**: cargo-dist
  releases major versions infrequently (a few per year); the manual
  re-pin pass takes ~5 minutes; an xtask would be 30+ lines of YAML-
  parsing + GitHub API code that itself needs maintenance + tests.
  YAGNI. CONTRIBUTING.md's "Updating cargo-dist" subsection
  documents the manual re-pin workflow for future maintainers.

## Consequences

**Positive:**

- Users get a one-line install that works on the 4 main developer
  platforms without requiring Rust toolchain.
- Supply chain is hardened against tag-rewrite attacks (D-6) while
  preserving rolling-toolchain semantics (rolling refs exempt).
- No crates.io commitment means lib API can keep evolving in v0.x
  without breaking external consumers (D-1, D-3).
- CHANGELOG is the single source of truth for what's in each release;
  GitHub Release notes derive from it (D-9).
- The 11-commit slicing means each commit is independently reviewable
  and revertible; the abort path (D-10) means a broken Stage 2 can't
  poison the release.

**Negative / risks:**

- **Repo slug risk** (D-2): if `agentprof/agentprof` is taken at
  registration, a coordinated rename pass is required before tag push.
  Spec §10 risk row + CONTRIBUTING.md cover the fallback. The risk is
  one-time (subsequent releases reuse the chosen slug).
- **Manual SHA-pin churn** (D-11): future cargo-dist upgrades require
  re-running the SHA-pin pass. Documented; ~5 minutes per upgrade;
  worth the simplicity vs an xtask.
- **No Windows users for v0.1.0** (D-5): closes a small percentage of
  the audience until v0.2+. Surfaced in README "Install" section as
  "Linux x86_64 / aarch64, macOS x86_64 / aarch64" so Windows users
  immediately see they're not supported (vs an install command that
  silently fails on Windows).
- **No GPG signing** (D-7): users with strict supply-chain policies
  can't verify binaries against a maintainer key. The SHA-256
  checksums protect against transport-layer tampering (and are
  themselves signed implicitly by HTTPS / the GitHub Release page's
  own URL signature). Future cosign / minisign adoption is
  non-breaking.

**Alternatives rejected:** see D-2, D-3, D-7, D-8, D-9, D-10, D-11
inline; see also spec §5.3 (excluded install paths: Homebrew, MSI,
Docker), spec §11 (out-of-scope: badges, RELEASING.md split, MSRV
policy doc).
