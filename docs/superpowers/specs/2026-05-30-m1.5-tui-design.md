# M1.5 — `agentprof-tui` design (events-first 适配版)

> **Status.** Approved 2026-05-30 (verbal approval per brainstorming session).
>
> **Scope.** Implement the ratatui TUI layer for `agentprof`, covering the 7 Task structure originally laid out in `tasks/001-mvp-agent-token-profiler.md` §10 M1.5, but **adapted to the events-first pivot** (ADR-0001) — i.e. without the tokenizer / `RoiScore` / cross-session aggregate that the original PRD assumed.
>
> **Authority.** This spec supersedes the M1.5 sub-task list in `tasks/001-*.md` §10 (which was written pre-pivot). The 001 file's M1.5 section will be marked "see this spec for the events-first refresh" when M1.5 ships.

## 0. TL;DR

`agentprof-tui` ships **3 views** rendered from a single `AnalysisReport`:

1. **FlamegraphView** — per-Turn horizontal gantt; each row = 1 Turn; segments = tool calls colored by `ToolSource`; whitespace = LLM thinking time; `ask_user` etc. textured; failed calls red.
2. **RoiView** — interactive `tool_rank` table; sort-key cycling (`1`=total, `2`=calls, `3`=success%, `4`=p50); bottom status bar shows recent N calls of the selected tool.
3. **AggregateView** — single-session aggregates: "By Mode" (interactive/plan/autopilot turn distribution) + "By Hook" (reuse `hook_rank`). No cross-session yet.

Entry: `agentprof analyze --export tui`. Panic-safe terminal lifecycle. ~3 insta snapshot tests (1 fixture × 3 views) + state-machine unit tests.

Tokenizer / `schema_utilization` / `waste_usd` are explicitly **not in M1.5** — Copilot wire does not broadcast tool schema definitions (verified empirically: `session.start` has no tools list; no event type carries `input_schema` / `parameters`). These deliverables wait for Phase 3 ClaudeAdapter where the wire format includes a tools array.

## 1. Context & motivation

**Why M1.5 design needs a refresh.** The original M1.5 in 001 §10 was drafted alongside the original product vision: Claude adapter + tokenizer + `RoiScore` 5-star ranking + cross-session aggregation. The events-first pivot (ADR-0001) substituted Copilot adapter as M1.2 and pushed tokenizer / ROI math to M1.5+ or Phase 2. Two of the original M1.5 deliverables ("FlamegraphView with 8 token-bucket coloring", "RoiView with ★★★★★ score") therefore lost their data foundation:

- FlamegraphView's `system / tools_schema / history / user / tool_result / output / cache_read / cache_creation` palette requires `count_tokens(...)` per bucket — we have no tokenizer.
- RoiView's `tokens_per_call = schema_tokens / call_count` ranking requires `schema_tokens(tool)` — we have neither the tokenizer nor the tool schema source (see "Data sources" below).

**Empirical Copilot wire limit (verified 2026-05-30).** A grep across an 11 806-line live session confirms:

- `session.start.data` keys: `sessionId`, `version`, `producer`, `copilotVersion`, `startTime`, `context.cwd`, `alreadyInUse`, `remoteSteerable`. **No tools list.**
- No event type carries `input_schema` / `parameters` / a tool definition body.
- `tool.execution_start` carries only the per-call payload (`toolCallId`, `toolName`, `arguments`, `turnId`), not the schema.

This means schema-token-based ROI is structurally impossible on the Copilot adapter regardless of whether we ship a tokenizer. The replacement path: use **call-time / call-count / success-rate / user-blocking** signals — all already computed by `analyzer::tool_rank`.

## 2. Goals

| ID | Goal | How M1.5 satisfies it |
|---|---|---|
| G-1 | First interactive view of a Copilot session | FlamegraphView shows per-turn timeline at a glance |
| G-2 | Surface "where is the agent burning time" | RoiView with sort-by-`total_duration` default + user-blocking split (carrying the M1.4 post-output-audit insight into the TUI) |
| G-3 | Reveal mode + hook patterns invisible in flat md table | AggregateView's "By Mode" shows whether the user is mostly in `interactive` / `plan` / `autopilot` and the cost of each |
| G-4 | Panic-safe (TUI must never leave terminal in raw mode) | `install_panic_hook` before `enter()`; `leave()` is idempotent; zero `unwrap()` in TUI code |
| G-5 | Re-use the same `AnalysisReport` other renderers consume | `AppRunner` only takes `&AnalysisReport`; no I/O inside TUI |

## 3. Non-goals (explicit YAGNI for M1.5)

- Tokenizer / `schema_utilization` / `waste_usd` (Phase 3 with ClaudeAdapter).
- Cross-session aggregate (M1.6 with `list` / `aggregate` subcommands).
- HTML / Speedscope export (M1.6).
- Mouse support (M1.5 = keyboard only).
- Search / filter / fuzzy navigation (M1.6+ if user demand surfaces).
- Live refresh / watch mode (Phase 2 with `watch` / `ingest-otlp`).
- Drill-down to specific tool call's arguments / result body (privacy + scope — never in TUI; users wanting raw event data run `--export json | jq`).

## 4. Architecture & data flow

```
                                   ┌─────────────────────────────────┐
agentprof analyze                  │ AppRunner                       │
  --export tui ──────────► loads ─►│   state: AppState               │
  (re-uses existing                │   terminal: enter/leave (RAII)  │
   --agent / --session              │   loop: poll(Event) → dispatch │
   / --root flags)                  │         → render(frame)         │
                                   │                                 │
                                   │   views/flamegraph              │
                                   │   views/roi                     │
                                   │   views/aggregate               │
                                   └─────────────────────────────────┘
                                          │
                                          └─► consumes only &AnalysisReport
```

**Layering invariant.** TUI is a pure renderer. It does not load sessions, does not call adapters, does not call `derive_episodes` or `analyze`. The CLI `cmd::analyze::run` performs those steps and hands the `AnalysisReport` in. This keeps TUI testable with synthetic reports and lets future consumers (e.g. M1.6 `watch` reading from SQLite) reuse the same `AppRunner` API.

## 6. View specifications

### 6.1 FlamegraphView

**Visual sketch:**

```
┌─ Flamegraph ─────────────────────────────────────────────────────────────────┐
│ Turn 1  9.6s  ████░░██▓▓███████░░░░░░                                       │
│ Turn 2  4.7s  █▓░░░░░░░░░                                                   │
│ Turn 3  11.6s ██▒▒▒▒░░░░░░░░░░░░░░░░░░░░ (1 FAIL)                          │
│ Turn 4  2.4m  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░ (ask_user)                          │
│ ...                                                                          │
│                                                                              │
│ Legend:  █ builtin    ▒ mcp    ▓ skill/user    ░ LLM-thinking    × failed   │
│ ⏱ 0s ━━━━━━━━━━━━━━━━━ max-turn-duration ━━━━━━━━━━━━━━━━━━━━━━━━━━━┓     │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **One row = one Turn**, in chronological order.
- **Row width**: scaled so the longest turn's duration fills the inner content area; all others scale proportionally.
- **Segments** within a row: one per `ToolCall` (using its `Span`), drawn at `(call.span.start - turn.start) / turn.duration` of the row width.
- **Whitespace** between/around segments = "LLM thinking time" (turn duration minus sum of tool call durations).
- **Color by `ToolSource`** (`theme.rs`):
  - `Builtin` → cyan
  - `Mcp` → magenta
  - `Skill` → yellow
  - `User` → blue
  - `Unknown` → gray
- **Modifiers**:
  - `ToolCallStatus::Failure { .. }` → segment background red (overrides source color)
  - `ToolEpisode.calls[*].turn_id` belongs to a tool in `USER_BLOCKING_TOOLS` (`ask_user`) → ratatui `Modifier::ITALIC` + slashed glyph
  - Aborted Turn → row underlined; status badge `[ABORTED]` after turn id
- **Scrolling**: vertical (up/down); long sessions paginate; viewport size is terminal rows.
- **Selection**: selected turn highlighted; bottom of pane shows `Turn N: model=... mode=... output_tokens=... tools=[...]`.

### 6.2 RoiView

**Visual sketch:**

```
┌─ RoiView ─ Sort: [1]total  2=calls  3=success%  4=p50 ────────────────────┐
│  #  Tool                                Source   Calls   OK  Fail   Total │
│ ►1  bash                               Builtin   1641   1641    0   57.4m │
│  2  task                               Builtin    137    137    0   4.90h │
│  3  sql                                Builtin     90     90    0   50.5m │
│  4  read_bash                          Builtin      7      7    0  46.62s │
│  ...                                                                       │
│                                                                            │
│ ── User-blocking tools (user think time) ────────────────────────────────  │
│  *   ask_user                          Builtin     61     61    0  69.43h │
│                                                                            │
│ ─ Selected: bash ──────────────────────────────────────────────────────── │
│   Recent: turn-1 (609ms✓)  turn-3 (1.2s✓)  turn-7 (412ms✓)  turn-12 (FAIL)│
└────────────────────────────────────────────────────────────────────────────┘
```

- **Top split**: work-tools table (sort-by selected; default `total_duration` desc).
- **Bottom split** (always visible): user-blocking tools (single section, sort hard-coded by `total_duration` desc; reflects the M1.4 post-output-audit decision to surface but not mix these into the headline rank).
- **Sort-key cycling**: keys `1` / `2` / `3` / `4` rebuild the work-tools sort:
  - `1` = `total_duration` desc (default)
  - `2` = `call_count` desc
  - `3` = `success_count / call_count` desc (then `call_count` desc tiebreak)
  - `4` = `p50_duration` desc
- **Row navigation**: ↑ / ↓ moves selection within work-tools.
- **Detail strip** (bottom 1-2 lines): for the currently selected tool, list the last 5 `ToolCall`s found in `Episodes.tools[name].calls` (turn id + duration + status badge). This is the only place TUI peeks into per-call data — no arguments, no results, only timing + status.

### 6.3 AggregateView

**Visual sketch:**

```
┌─ Aggregate (single session) ────────────────────────────────────────────────┐
│ ## By Mode                                                                  │
│   Mode         Turns    Total dur    Total tokens    Tools    Avg tools/t  │
│   interactive    821    6.2h         412.3k          1822     2.2           │
│   plan            78    28m          41.2k           240      3.1           │
│   autopilot       29    12m          18.7k           67       2.3           │
│                                                                             │
│ ## By Hook                                                                  │
│   Hook          Calls   Success   Fail   p50      Total                     │
│   postToolUse    965    965         0    0ms      27ms                      │
│   sessionStart     2      2         0   52ms      92ms                      │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **Data source**: derive from `AnalysisReport.turn_summary` (group by `mode`) + `AnalysisReport.hook_rank` (no grouping; direct render).
- **No cross-session aggregation**. The "single session" label is explicit in the header so users don't confuse this with the future M1.6 cross-session aggregate.
- **Sub-headings render in bold** via ratatui `Modifier::BOLD`; the `## ` markdown sigil is dropped in TUI.

## 7. Key bindings

> **Note (post-shipping, supersedes this section)**: After M1.5 shipped, two user-reported UX bugs were fixed in commits `c53458d` and the follow-up. Final bindings:
> - `1` / `2` / `3` **ALWAYS** switch view (no Roi exception — the conflict rule below is obsolete).
> - `t` / `c` / `s` / `p` cycle RoiView sort (`total / calls / success% / p50`); ignored outside Roi.
> - `↑` / `↓` use edge-triggered viewport scroll (cursor moves freely within visible window; viewport only scrolls when cursor leaves window).
>
> See `dispatch()` doc-comment in `crates/agentprof-tui/src/app/state.rs` for the current source of truth. Section §7 below is preserved verbatim for spec-history continuity.

| Key | Action |
|---|---|
| `q` / `Ctrl-C` | Quit (clean leave + exit 0) |
| `1` | Switch to FlamegraphView |
| `2` | Switch to RoiView |
| `3` | Switch to AggregateView |
| `Tab` | Cycle to next view |
| `Shift-Tab` | Cycle to previous view |
| `↑` / `↓` | Scroll / selected-row navigation |
| `←` / `→` | Horizontal scroll (Flamegraph long-turn navigation only) |
| `1`-`4` (in RoiView) | Cycle sort key (top-level number keys reused — RoiView wins if focused, else view-switch) |
| `?` | Help overlay (modal; any key dismisses) |

> **Conflict resolution for `1`-`4`**: top-level number keys `1`/`2`/`3` switch view UNLESS the current view is RoiView, in which case they re-sort. `?` overlay disables all other key handling. This is documented in the help overlay text.

## 8. State machine

`AppState` is the single source of truth. All inputs flow through `fn dispatch(&mut AppState, Event) -> Option<Action>` where `Action::Quit` triggers the run loop exit.

```rust
pub struct AppState<'a> {
    pub view: View,
    pub scroll: HashMap<View, (u16, u16)>,
    pub roi_sort: SortKey,
    pub roi_selected: usize,
    pub flame_selected: usize,
    pub help_open: bool,
    pub report: &'a AnalysisReport,
}

pub enum Action { Quit, None }
pub enum View { Flamegraph, Roi, Aggregate }
pub enum SortKey { TotalDur, Calls, SuccessRate, P50 }
```

**State transition tests** to lock in `state::tests`:

- `view_switch_via_number_keys_1_2_3`
- `tab_cycles_views_forward_and_backward`
- `scroll_saturates_at_top_and_bottom`
- `roi_sort_key_cycle_1_to_4`
- `roi_selected_row_navigation`
- `ctrl_c_emits_quit_action`
- `help_overlay_swallows_other_keys`
- `quit_q_emits_quit_action`
- `number_keys_1_to_4_in_roi_view_sort_not_switch` (covers the §7 conflict-resolution rule)

## 9. Panic safety (hard requirement)

This is the only `agentprof-tui` behavior that can corrupt the user's terminal session. It MUST be correct.

**Order of operations in `main()`** (added in T6 to `crates/agentprof-cli/src/main.rs` for the `--export tui` branch):

```rust
agentprof_tui::install_panic_hook();   // BEFORE enter()
let mut term = agentprof_tui::enter()?;
let result = AppRunner::new(report).run(&mut term);
agentprof_tui::leave(&mut term)?;      // best-effort even on Err
result
```

- `install_panic_hook` wraps the existing hook so that on panic it (1) restores the terminal (`disable_raw_mode` + `LeaveAlternateScreen`) and (2) invokes the original hook to print the panic message in cooked mode. The original hook's default unwind/abort behavior is preserved unchanged — see [ADR-0006](../../internals/adr-0006-panic-safe-tui.md) for canonical lifecycle and the "Why a `Once` guard" / "Why not RAII" rationales.
- `leave()` is idempotent: calling it twice or without `enter()` does not panic. Verified by `terminal::tests::leave_without_enter_does_not_panic` (mock backend).
- Zero `unwrap()` in TUI code (already enforced by workspace `clippy.unwrap_used = "deny"` per `Cargo.toml`).

**Ctrl-C handling**: the `crossterm` event loop receives Ctrl-C as a normal `KeyEvent` (KeyCode::Char('c') + KeyModifiers::CONTROL); `dispatch` maps it to `Action::Quit`. SIGINT outside the loop (e.g. during `enter()`) is rare; not handled in M1.5.

## 11. CLI integration (T6)

`crates/agentprof-cli/src/cmd/analyze.rs`:

- Add `Tui` variant to existing `ExportFormat` enum (currently `Md` / `Json`).
- `--export` clap variant accepts `tui` value.
- In `cmd::analyze::run`, after `let report = analyze(...)`:
  ```rust
  match cmd.export {
      ExportFormat::Md => render_md_and_write(...),
      ExportFormat::Json => render_json_and_write(...),
      ExportFormat::Tui => {
          if !std::io::stdout().is_terminal() {
              return Err(ExitKind::OutputError.into_anyhow(
                  "--export tui requires a TTY; use md or json for piped output"
              ));
          }
          agentprof_tui::install_panic_hook();
          let mut term = agentprof_tui::enter()?;
          let res = agentprof_tui::AppRunner::new(&report).run(&mut term);
          let _ = agentprof_tui::leave(&mut term);
          res?
      }
  }
  ```

`--section` flag is silently ignored when `--export tui` (TUI shows all 3 views regardless; clarify in `--help`).

## 13. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| ratatui major version churn breaks compile mid-development | Low | Pin to current workspace ratatui version (already done); refresh at most once per M1.x |
| `install_panic_hook` ordering subtle, terminal stuck in raw mode on crash | High if mis-ordered | ADR-0006 documents exact order; manual test in §10; CI cannot test this directly |
| Snapshot tests flaky across ratatui versions (different default styles) | Medium | Limit to 3 snapshots; use `INSTA_UPDATE=always` for routine refresh; spot-review before commit |
| Flamegraph rendering math wrong for edge cases (zero-duration turns, missing call spans) | Medium | Cover with unit tests on the segment-layout function; explicit handling for `duration.is_zero()` → skip whitespace; degenerate-turn snapshot |
| Long tool names blow out RoiView column width | Medium | Truncate with `…` at fixed column width; full name visible in detail strip |
| `analyze --export tui` invoked under non-tty errors confusingly | Medium | Explicit error message in §11 |
