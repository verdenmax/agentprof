## 1. Problem statement

The M2.2 OTLP receiver shipped to `main` (HEAD `0838827`) is functionally complete but
has three open security gaps surfaced by the post-merge audit:

- **F1** — Bearer token comparison uses `==` (timing oracle).
- **F2** — No body/decoded-message size cap on either gRPC or HTTP listeners; a single
  protobuf bomb (deeply nested repeated `KeyValue` lists) can decode into hundreds of
  MiB before the per-session buffer cap triggers.
- **F3** — `SessionRouter` has no cap on the number of distinct sessions it tracks.
  UUID-spam exhausts memory before the idle sweeper (30 s default) gets a chance.

Combined, F2 + F3 allow a small number of crafted requests to OOM the process.
F1 is independent but allows offline bearer recovery given network timing access.

Additionally, the audit found two minor but user-impacting issues:
- **F4** — `Cargo.toml` + `README.md` still claim v0.1.0 despite M2.1 / M2.1.1 / M2.2
  having merged. `cargo install` from `main` reports the wrong version.
- **F7 / F8** — `docs/architecture.md` §3 lists modules that don't exist;
  `docs/plan.md` M2.1.1 entry says "commit pending merge" but it's merged.

This spec covers the **OTLP hardening fixes** (M2.4) plus the **release cadence** that
groups the shipped-and-unreleased work into proper SemVer tags.

## 3. Design decisions

### Decision 1 — F3 eviction strategy: **LRU evict** (vs refuse / hybrid / no-op)

**Choice:** When `SessionRouter` hits `max_open_sessions`, immediately flush the
least-recently-active buffer with new `CloseReason::CapacityEvict`, then accept the
new session.

**Alternatives considered:**
- **Refuse new** — return `tonic::Code::ResourceExhausted` / HTTP 503. Cleaner
  semantically (honest about saturation) but rejects legitimate traffic during
  bursts (e.g., 3 agents starting simultaneously while idle sweeper is mid-cycle).
- **Hybrid** — try LRU evict first; if oldest is fresh (< 1 s grace period), refuse.
  Combines both approaches but adds complexity for marginal benefit.
- **No-op (log warn only)** — current behavior; trust idle sweeper. Fails because
  attacker can keep buffers warm with trickle traffic to defeat the timer.

**Rationale for LRU:** Smooth degradation, no client-visible errors during normal
bursts, evicted sessions are still persisted (just earlier than they'd otherwise
be). The `CapacityEvict` close reason gives users a clear post-hoc signal in DB.

### Decision 2 — F2 cap values: **per-signal split (8 / 2 / 8 MiB)**

**Choice:** Three independent config fields applied to both transports:
- `max_logs_request_bytes`   = `8 * 1024 * 1024`
- `max_metrics_request_bytes` = `2 * 1024 * 1024`
- `max_traces_request_bytes`  = `8 * 1024 * 1024`

**Alternatives considered:**
- **Uniform 4 MiB** — matches tonic default; simpler config; less DoS protection on
  metrics (which are typically tiny).
- **Uniform 8 MiB** — generous; uniform mental model; lets metrics bombs through.
- **Uniform 16 MiB** — matches per-session buffer cap; simplest mental model
  ("one request can fill one buffer") but weak against decode-amplification.

**Rationale for per-signal:** Metric envelopes are routinely 10–100× smaller than
log/trace envelopes in real OTel traffic. Tight metrics cap is essentially free
defense-in-depth.

### Decision 3 — F3 default `max_open_sessions`: **1024**

**Choice:** Default to 1,024 distinct concurrent sessions.

**Alternatives considered:**
- **256** — safer for laptops; covers 99% of single-developer setups (most users
  run ≤ 5 concurrent agents) with comfortable headroom.
- **64** — tight; triggers LRU evict often in CI/test scenarios.
- **4096** — only sensible for dedicated server / k8s pod with explicit resource
  limits.

**Rationale for 1024:** With 16 MiB per-buffer cap, worst-case memory is 16 GiB —
appropriate for team-shared deployments. Single-user setups will never approach
the cap. Operators with stricter memory budgets override via `--max-open-sessions`.

### Decision 4 — F1 primitive: **`subtle` crate**

**Choice:** Add `subtle = "2"` to `[workspace.dependencies]`; use
`subtle::ConstantTimeEq` in `auth.rs`.

**Alternatives considered:**
- **Hand-roll constant-time u8 slice compare** — ~10 lines, no new dep, but
  reinvents a solved problem; harder to convince reviewers it's correct.
- **`ring::constant_time::verify_slices_are_equal`** — already in tree
  transitively via rustls; avoids new direct dep but couples auth to ring's
  public API surface (which is intentionally minimal and may not stay stable).

**Rationale for `subtle`:** De facto standard, zero transitive deps, well-audited
by the dalek-cryptography team, MSRV 1.60 (under our 1.78). Negligible build
cost; high security clarity.

### Decision 5 — `SessionId` length cap: **256 bytes at mapper layer**

**Choice:** Add `MapperError::SessionIdTooLong { len: usize }`; reject session IDs
longer than 256 bytes before they reach the router. 256 bytes accommodates UUIDv4
(36 chars) with 7× headroom, easily covers any sane prefix scheme.

**Alternatives considered:**
- **No cap** — pathological 1 MB session IDs amplify F3 attack.
- **Cap at router insert** — works but error reporting is muddier (router doesn't
  see the source signal type).

**Rationale:** Mapper is the only correct layer — it has access to source signal
metadata for the error message and runs before any buffer allocation.

### Decision 6 — Release cadence: **three tags (v0.2.0 → v0.2.1 → v0.3.0)**

**Choice:**
- `v0.2.0` = M2.1 (SQLite persistence) + M2.1.1 (aggregate dual-path)
- `v0.2.1` = M2.2 OTLP receiver as-shipped, **with prominent security notice**
  in release notes pointing at v0.3.0 for OTLP users
- `v0.3.0` = M2.4 OTLP hardening

**Alternatives considered:**
- **Single v0.3.0** — one tag covering everything; simplest CHANGELOG.
- **Two tags (v0.2.0 + v0.3.0)** — skip v0.2.1; only release hardened OTLP.

**Rationale for three tags:** Each tag represents a coherent unit of value with a
clear upgrade story. The v0.2.1 → v0.3.0 minor bump (not patch) signals "this is
not just a bug fix; if you use OTLP, upgrade." Skipping v0.2.1 would hide the
fact that the unhardened OTLP receiver was ever in main, which complicates bug
triage for users running git checkouts between merges.

### 4.2 `CloseReason`

```rust
// crates/agentprof-storage/src/otlp/router.rs
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum CloseReason {
    ExplicitEnd,
    OomBytes,
    OomEvents,
    Idle,
    Shutdown,
    CapacityEvict, // NEW: SessionRouter exceeded max_open_sessions and evicted oldest
}
```

`StorageFlushSink` treats `CapacityEvict` identically to `Idle` for persistence
(session row written, no error to client). The reason is logged at `info` level
for operator visibility.

### 4.3 `MapperError`

```rust
// crates/agentprof-storage/src/otlp/error.rs
#[non_exhaustive]
pub enum MapperError {
    // … existing variants …
    SessionIdTooLong { signal: SignalKind, len: usize },
}
```

### 4.4 `SessionRouter` internals (private; no public API change)

Adds an LRU tracking structure. Two implementation options will be evaluated in
the plan:
- **Option A:** `parking_lot::Mutex<lru::LruCache<SessionId, ()>>` — pulls in `lru`
  crate (~50 lines, no deps, well-maintained).
- **Option B:** Roll our own — maintain a sorted `BTreeMap<Instant, SessionId>` of
  last-touch times alongside the `DashMap`; on insert/touch, update both.

Option A is preferred for clarity; Option B avoids a dep but adds ~80 lines of
custom code. Plan will pick during implementation.

### 4.5 CLI

```
agentprof ingest-otlp [existing flags …]
```

## 5. Wire-up changes

### 5.1 `auth.rs`
Replace 2 call sites of `token == expected.as_str()` with
`subtle::ConstantTimeEq::ct_eq(token.as_bytes(), expected.as_bytes()).into()`.

### 5.2 `server_grpc.rs`
For each of `LogsServiceServer`, `MetricsServiceServer`, `TracesServiceServer`,
wrap with `.max_decoding_message_size(cfg.max_X_request_bytes)`.

### 5.3 `server_http.rs`
For each of `POST /v1/logs`, `POST /v1/metrics`, `POST /v1/traces`, apply
`axum::extract::DefaultBodyLimit::max(cfg.max_X_request_bytes)` via
`Router::layer(...)` per route.

### 5.4 `router.rs`
Add private `LruIndex` field. In `ingest`, after grouping events by `session.id`,
on insert into `buffers`:
1. If `buffers.len() >= cap.max_open_sessions` and session is new → evict oldest
   via `close_buffer(oldest_id, CapacityEvict)`.
2. Touch LRU index with current `Instant`.

### 5.5 `mapper.rs`
In `extract_session_id`, after deriving the candidate `session_id`, check
`if candidate.len() > 256 { return Err(MapperError::SessionIdTooLong { … }); }`.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| `subtle` crate is unmaintained / yanked | Pin to `2.5` (current stable, last published 2024); revisit annually. Low-risk: zero deps, well-tested. |
| LRU eviction causes data loss for legit long-lived sessions during burst | Default cap 1024 is generous; eviction always persists via flush sink (lossy only on in-flight events not yet flushed within evicted buffer). Document trade-off in ADR-0022. |
| `lru` crate adds dep weight | Tiny (no transitive deps, ~50 lines actual code). Acceptable. |
| Per-signal caps confuse operators (3 knobs vs 1) | Sensible defaults rarely need overriding; document with examples in agentprof-cli README. |
| Tonic `max_decoding_message_size` API behavior differs between 0.12 and 0.13 | Pin to current tonic 0.12; test in CI; only revisit on tonic bump. |
| v0.2.1 release of known-vulnerable OTLP confuses users | Loud SECURITY NOTICE in release notes; v0.3.0 follows within days, not weeks. |
| Breaking deserialization of `OtlpServerConfig` due to new fields | `PartialOtlpServerConfig` uses `#[serde(default)]` on each field; missing keys → default values. Existing config files keep working. |
