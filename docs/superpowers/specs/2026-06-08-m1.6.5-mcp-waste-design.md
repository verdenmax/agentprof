# M1.6.5 — MCP server waste analysis (counts-only Phase 1)

**Date**: 2026-06-08
**Topic ID**: `m1.6.5-mcp-waste`
**Pipeline stage**: brainstorming → spec → ADR-0015 (to be drafted) → writing-plans → implementation
**Companion follow-up**: M1.6.6 (token-cost waste — `tiktoken-rs` × actual `mcp.json` tool descriptions)
**Prior milestones**: M1.6.4 (Speedscope + HTML export + tracing) — v0.1.0 shipped

> **TL;DR** — Quantify "MCP context bloat": which MCP servers / tools the
> agent had access to but never actually called within a session
> (`unused = loaded − called`). Two data sources with a fallback chain:
> wire-parsed `<tools_changed_notice>` blocks embedded in
> `user.message.transformedContent` (primary, always available on Copilot
> CLI ≥ 1.0.x) + `~/.copilot/mcp.json` (optional baseline). Four surfaces:
> new `analyze --section mcp-waste` (single session), extended columns on
> `aggregate --by mcp-server` (cross-session), new `agentprof mcp-waste`
> subcommand (專題 cross-session), and a 5th TUI view (key `5`,
> split-pane like Models view). Token-cost view (the "C" angle from
> brainstorming) deferred to M1.6.6 — keeps mcp.json schema-variation
> risk isolated. Estimated 1.5 days of implementation; ~47 new tests.

## 1. The problem

### 1.1 What "waste" means in agentprof

`agentprof` is the agent-token-profiler that turns Copilot CLI session
logs into a flamegraph + ROI report. Per `docs/plan.md` §0:

> 「市面同类工具只算"花了多少 token"，本项目算"**花得值不值**"。」

The "ROI" view (`agentprof analyze --section tool-rank --export tui`,
key `2`) already answers _"of the tools you called, which ones returned
useful results"_ via `success_rate` / `p50_duration` / `call_count`.
**M1.6.5 fills the missing other half**: tools you DIDN'T call but were
nevertheless paying for (in context window, in setup latency, in
mental load). That set is invisible in today's ROI table.

### 1.2 Who asks this question

Three personas, three pain points:

| User | Question | Today's answer |
|---|---|---|
| MCP server admin | "Which servers can I remove from my `mcp.json` because nothing ever uses them?" | manual log scan |
| Tool author | "Did the agent ever invoke MY tool in this session?" | manual grep |
| Power user | "Why is my context window so full? What % of it is unused tool descriptions?" | unanswerable today |

M1.6.5 answers the first two directly (count-based). M1.6.6 answers the
third (token-cost based).

### 1.3 Why now

The infrastructure to do this landed across M1.2 (CopilotAdapter) and
M1.6.2 (`aggregate --by mcp-server` + `ToolSource::Mcp { server }`).
The MCP grouping is already implemented; what's missing is the *loaded*
counterpart so we can compute the difference `loaded − called`. That
counterpart turned out to be available on the wire (see §3.1).

## 3. Data sources

### 3.1 Wire source: `<tools_changed_notice>`

**Discovery (2026-06-08 audit on real `~/.copilot/session-state/` data):**
Copilot CLI **does** record tool-availability changes on the wire, but
they're embedded inside `user.message.data.transformedContent` as
XML-like blocks, not as standalone event types.

```text
<tools_changed_notice>
New tools available: exit_plan_mode, mcp__github__search_issues

Tools no longer available: legacy_tool_name
</tools_changed_notice>
```

Multiple blocks may appear in one `transformedContent`. The block
positions are unpredictable (sometimes at the very start, sometimes
mid-text). Tool names are comma-separated within the "New tools
available:" or "Tools no longer available:" lines.

### 3.2 Config source: `~/.copilot/mcp.json` (optional baseline)

Static configuration for which MCP servers the user has registered with
the Copilot CLI. Two common schema flavors (we tolerate both
best-effort; the loader degrades gracefully on unknown schemas — see §6.2):

**VSCode-flavored** (the format Copilot CLI inherits from VSCode):
```json
{
  "mcpServers": {
    "github": { "command": "npx", "args": ["-y", "@github/mcp-server"] }
  }
}
```
Server names only — no enumeration of the tools each server provides.

**Self-describing** (hand-crafted variant; not observed in real Copilot
data during the 2026-06-08 audit but supported defensively):
```json
{
  "servers": {
    "github": {
      "tools": ["search_issues", "create_pr", "delete_branch"]
    }
  }
}
```
Includes per-server tool lists. When this shape is present, we can
detect tools that the user **configured** but the agent never even saw
on the wire — the strongest "remove me from mcp.json" signal.

### 3.3 Fallback chain

```text
Try `~/.copilot/mcp.json` (or `--mcp-config <path>` override)
  → if absent: config_loaded = None
  → if present but unparseable: log warn, config_loaded = None
  → if parseable: config_loaded = Some(ParsedMcpConfig)
                  ├─ server names always extracted
                  └─ tool lists per server when schema allows

Always parse wire `<tools_changed_notice>` blocks
  → wire_loaded = BTreeSet<String> of "ever-advertised" MCP tools

Always derive called set from existing report.tool_rank
  → called = BTreeMap<server, BTreeMap<tool, call_count>>

Final loaded set per (server, tool) = (wire ∪ config_tools ∪ called.keys)
  → each tool tagged with LoadedSource provenance
```

### 3.4 Data availability matrix → WasteDataSource

| wire ≥1 notice | mcp.json present | → `WasteDataSource` | report mode |
|---|---|---|---|
| ✓ | ✓ | `Both` | full report (server + tool granularity) |
| ✓ | ✗ | `Wire` | full report (mcp.json fallback inactive) |
| ✗ | ✓ | `Config` | server-level only when `ServerInfo.tools = None`; full when explicit |
| ✗ | ✗ | `None` | banner: "MCP waste analysis requires Copilot CLI ≥ 1.0.x emitting `<tools_changed_notice>` OR `~/.copilot/mcp.json`. Neither found." |

**Crate-boundary invariants (per §3 of `docs/architecture.md`):**
- `agentprof-core` is a leaf (no workspace deps). `compute_waste` is a
  pure function: caller (cli) constructs `wire_loaded` and
  `config_loaded` and passes them in. Core does not know about file
  paths or adapter-specific wire formats.
- `agentprof-adapters::copilot` owns Copilot-specific extraction (wire
  + mcp.json). Future Claude / Codex adapters provide equivalents via
  their own `tools_changed` / `mcp_config` modules.
- `agentprof-cli` is the only glue layer that wires adapter output
  into core algorithms.

## 5. Data model

### 5.1 New core types (`agentprof_core::model::waste`)

```rust
/// Per-session MCP-server-waste report.
///
/// "Loaded" = wire ∪ config_tools ∪ called.keys (union semantics — any
/// tool ever observed in any of the three sources is considered loaded).
/// "Called" = MCP tools with ≥ 1 `tool.execution_start` event.
/// "Unused" = loaded ∖ called.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[non_exhaustive]
pub struct WasteReport {
    /// Per-server breakdown, sorted by `unused_count` descending.
    pub server_waste: Vec<McpServerWaste>,
    /// Provenance of the loaded-set inputs — drives the UI "data
    /// availability" banner.
    pub data_source: WasteDataSource,
    /// Sum across all servers.
    pub total_loaded_tool_count: usize,
    /// Sum across all servers.
    pub total_unused_tool_count: usize,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[non_exhaustive]
pub struct McpServerWaste {
    /// Server prefix (e.g. `"github"`, `"filesystem"`).
    pub server: String,
    /// Tools belonging to this server, sorted by `short_name` ascending.
    pub tools: Vec<McpToolWaste>,
    pub loaded_count: usize,
    pub called_count: usize,
    /// = loaded_count - called_count
    pub unused_count: usize,
    /// True iff `called_count == 0` — entire server received zero calls.
    pub is_fully_unused: bool,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[non_exhaustive]
pub struct McpToolWaste {
    /// Full wire name: `mcp__<server>__<tool>` (e.g.
    /// `mcp__github__search_issues`).
    pub tool_name: String,
    /// Trailing component after the second `__` separator
    /// (e.g. `search_issues`). Pre-computed for ergonomic rendering.
    pub short_name: String,
    /// 0 ⇒ this tool was loaded but never called.
    pub call_count: usize,
    /// Which sources contributed this tool to the loaded set.
    pub loaded_source: LoadedSource,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[non_exhaustive]
pub enum LoadedSource {
    /// Seen only in wire `<tools_changed_notice>`.
    Wire,
    /// Seen only in `mcp.json`.
    Config,
    /// Seen in both.
    Both,
    /// Not in wire or config but was called — inferred as loaded.
    /// Indicates a parsing gap in the loaded-set extractors.
    InferredFromCall,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[non_exhaustive]
pub enum WasteDataSource {
    /// Neither wire notices nor mcp.json found — report is empty +
    /// banner explains the requirement.
    None,
    /// Only wire notices present (mcp.json missing / unparseable).
    Wire,
    /// Only mcp.json present (no wire notices — older Copilot CLI?).
    Config,
    /// Both sources contributed.
    Both,
}
```

## 6. Algorithm

### 6.1 Wire `<tools_changed_notice>` parser
`agentprof_adapters::copilot::tools_changed`

```rust
/// Walk a session's events, extract every `<tools_changed_notice>`
/// block from any `user.message.transformedContent`, accumulate the
/// "ever loaded" MCP tool set.
///
/// **Semantics (M1.6.5):** "loaded" = "ever appeared in a
/// `New tools available:` line". `Tools no longer available:` lines
/// are parsed but do NOT remove from the set — this is by-design for
/// the "did the agent ever have access" question. M1.6.6+ may add a
/// `LoadedWindow` model that tracks the time intervals during which
/// each tool was accessible.
pub fn extract_loaded_set_from_session(
    events: &[CopilotEvent],
) -> BTreeSet<String> {
    let mut acc = BTreeSet::new();
    for ev in events {
        if let CopilotEvent::UserMessage(env) = ev {
            for block in find_tools_changed_notices(&env.data.transformed_content) {
                acc.extend(parse_new_tools_line(block));
            }
        }
    }
    // Only MCP tools (`mcp__<server>__<tool>`) are subject to waste
    // analysis. Builtin (`bash`, `edit`, `exit_plan_mode`) and skill
    // (`skill__<plugin>__<name>`) tools are out of scope.
    acc.retain(|n| n.starts_with("mcp__"));
    acc
}
```

**Parsing detail:**
- `find_tools_changed_notices(s)` uses plain `str::find` for
  `<tools_changed_notice>` / `</tools_changed_notice>` — no regex
  dependency. Tolerates blocks that appear anywhere in the content.
- `parse_new_tools_line(block)` scans `block` line-by-line for the
  prefix `"New tools available:"`, splits the remainder on `, `,
  trims each entry, filters to `[A-Za-z0-9_-]+` (whitelist).
- Multiple `New tools available:` lines in one block are all accumulated.
- `Tools no longer available:` lines are silently skipped (parsed but
  not used — see semantics note above).

### 6.2 `mcp.json` loader
`agentprof_adapters::copilot::mcp_config`

```rust
/// Best-effort parse of `~/.copilot/mcp.json` (or override path).
/// Returns `None` if the file doesn't exist, can't be read, or fails
/// to parse — caller must treat that as "config baseline unavailable"
/// and rely on the wire source.
///
/// # Errors
///
/// **Never returns Err**. All failures (missing file, IO error, JSON
/// parse error, unknown schema) degrade gracefully to `None` after
/// emitting a `tracing::warn!`. Caller cannot distinguish "absent" from
/// "broken" — this is intentional: the wire path is the authoritative
/// source, so distinguishing helps nobody.
pub fn load_mcp_config(path: &Path) -> Option<ParsedMcpConfig> { /* ... */ }

pub struct ParsedMcpConfig {
    pub servers: BTreeMap<String, ServerInfo>,
}

pub struct ServerInfo {
    /// `None` ⇒ schema enumerates only the server name (most common),
    ///         so per-tool waste is wire-only for this server.
    /// `Some(...)` ⇒ schema lists the server's tools — we can detect
    ///         tools that the user *configured* but the agent never
    ///         even saw on the wire (the strongest "remove me" signal).
    pub tools: Option<Vec<String>>,
}
```

**Schema detection (tried in order):**
1. Self-describing: top-level `servers: { <name>: { tools: [...] } }`
2. VSCode-flavored: top-level `mcpServers: { <name>: { command, args, ... } }`
3. Unknown: empty `ParsedMcpConfig` + `tracing::warn!`

### 6.3 `compute_waste` core function
`agentprof_core::analyzer::waste`

```rust
#[tracing::instrument(name = "analyzer.waste", skip_all)]
pub fn compute_waste(
    report: &AnalysisReport,
    wire_loaded: &BTreeSet<String>,
    config_loaded: Option<&BTreeMap<String, Vec<String>>>,
) -> WasteReport { /* ... */ }
```

Algorithm:
1. **Build `called` map**: iterate `report.tool_rank`, filter
   `matches!(row.source, ToolSource::Mcp { .. })`, group as
   `BTreeMap<server, BTreeMap<tool, call_count>>`.
2. **Construct `loaded` super-set** with provenance:
   - Start from `wire_loaded`, tag each `LoadedSource::Wire`.
   - For each `(server, tools)` in `config_loaded.unwrap_or_default()`:
     - For each tool: synthesize full name `mcp__<server>__<tool>`,
       upgrade existing `Wire` entries to `Both`, insert new ones as
       `Config`.
   - For each called tool not yet in the set: insert as
     `InferredFromCall`.
3. **Group `loaded` by server prefix** (`mcp__<server>__<tool>` →
   `<server>`), build a `McpServerWaste` per server with sorted tools.
4. **Sort** `server_waste` by `unused_count` descending,
   ties by `server` ascending.
5. **Compute `data_source`** discriminant from
   `(wire_loaded.is_empty(), config_loaded.is_some())`.

Complexity: `O(loaded + called)` — sub-millisecond for any realistic
session size.

### 6.4 `aggregate_waste` cross-session reducer

```rust
pub fn aggregate_waste(
    per_session: &[(SessionRef, WasteReport)],
) -> AggregateWasteReport { /* ... */ }
```

Algorithm:
1. **Per-server roll-up**: walk each session's `server_waste`,
   accumulate `sessions_loaded` (count of sessions where the server
   appeared in `WasteReport`), `sessions_with_zero_calls` (count of
   sessions where `is_fully_unused`).
2. **Per-tool roll-up** (per server): walk each session's
   `McpServerWaste.tools`, accumulate `sessions_loaded`,
   `sessions_called` (count of sessions where `call_count > 0`),
   `total_call_count` (sum).
3. **Compute `never_called_tools`**: tools with
   `sessions_called == 0 && sessions_loaded > 0`, sorted alphabetically.

Same `O(n)` complexity as `aggregate_by_mcp_server` — runs in same
order of magnitude as existing aggregate (~1s for 100 sessions).

## 8. Edge cases & error handling

### 8.1 Data availability matrix → UI behavior

| `WasteDataSource` | UI |
|---|---|
| `Both` | Full report, banner: "Data source: wire (N) + mcp.json" |
| `Wire` | Full report, banner: "Data source: wire (N notices)" |
| `Config` | Server-level only, banner: "Data source: mcp.json (tool-list parse limited; per-tool waste needs Copilot CLI ≥ 1.0.x)" |
| `None` | Empty report + banner: "MCP waste analysis requires Copilot CLI ≥ 1.0.x emitting `<tools_changed_notice>` OR `~/.copilot/mcp.json`. Neither found in this session." Exit 0 (not an error). |

### 8.2 Parse failure degradation

| Failure | Behavior |
|---|---|
| Malformed `<tools_changed_notice>` (no close tag, weird encoding) | Skip block, `tracing::warn!(line_no, "malformed tools_changed_notice")`. Ledger only — does not abort session analysis. |
| `mcp.json` exists but JSON parse fails | `tracing::warn!`, treat as missing (`config_loaded = None`). |
| `mcp.json` parsed but neither VSCode nor self-describing schema | Empty `ParsedMcpConfig`, `tracing::warn!`. |
| Tool name with illegal chars (`mcp__server__../etc/passwd`) | Filtered by `[A-Za-z0-9_-]+` whitelist. |
| `user.message.data.transformed_content` field missing entirely | Treat as empty string, 0 notices. |

### 8.3 TTY check (consistent with §11 of `docs/architecture.md`)

- `agentprof mcp-waste --export {md,json,html}` writes to stdout (or
  `--output` file). **No TTY check** — fully scriptable.
- `agentprof analyze --export tui` (route into MCP Waste view via
  key `5`) reuses the existing `analyze::run_tui` TTY check
  (`stdin().is_terminal() && stdout().is_terminal()`).

### 8.4 Exit codes (per §11 of `docs/architecture.md`)

| Scenario | exit code |
|---|---|
| Successful report (even if waste found — that's the point!) | 0 |
| No sessions match `--since` / `--root` | 2 (data) |
| Explicit `--mcp-config <path>` given but file unreadable | 1 (user) |
| All sessions failed to parse | 2 (data) |
| Ctrl-C | 130 (SIGINT) |

### 8.5 Performance

Empirically estimated upper bounds:

| Operation | Input | Time |
|---|---|---|
| Wire `<tools_changed_notice>` scan per session | ~5K events, avg 1 KB `transformed_content` | < 10 ms |
| `mcp.json` load + parse | < 100 KB JSON | < 1 ms |
| `compute_waste` per session | < 100 MCP tools | < 0.1 ms |
| `mcp-waste --since 30d` over 100 sessions | 100 × ~10 ms | ~ 1 s |

No new hot path; no benchmark suite needed.
