## 1. Problem statement

AgentProf today exposes session data through **5 read surfaces**:

1. `analyze --export {md,html,json,speedscope}` — single-session report
2. `list` — table of sessions
3. `aggregate --by {tool,mcp-server,day,model} --export {md,csv,html,tui}` — cross-session rollup
4. `mcp-waste` — MCP server waste analysis (+ TUI key `5`)
5. TUI views (`watch`, `analyze --export tui`, `aggregate --export tui`) — live + interactive but terminal-bound

**Gap (Q-7.2 from docs/plan.md)**: there is no way to monitor an agent's session activity in a browser tab. The closest equivalent is `agentprof watch <session-id>` in a separate terminal, or rerunning `agentprof analyze --export html` and reloading the static file. Neither is a comfortable "second monitor" experience: TUI is terminal-bound, static HTML is stale until manual rerun.

This spec proposes `agentprof serve`: an embedded HTTP server that renders the same data the existing CLI surfaces produce, with browser-driven auto-refresh (default 5 s poll, user-configurable from 1 s to off).

## 2. Scope

### In scope

- New `agentprof serve` subcommand (parallel naming to `agentprof ingest-otlp` from M2.2).
- HTTP server bound to `127.0.0.1:4329` by default; `--bind` flag overrides.
- 5 server-rendered HTML views matching the existing read surfaces:
  - Sessions list (mirrors `agentprof list`).
  - Single session detail (mirrors `agentprof analyze --export html`).
  - Cross-session aggregate (mirrors `agentprof aggregate --export html`; supports `--by tool/mcp-server/day/model`).
  - MCP-waste server list.
  - MCP-waste server detail.
- Vanilla-JS polling layer (~80 LOC, no framework): `setInterval(fetch())` swapping HTML chunks via `innerHTML`. Toolbar with pause + interval picker (1 s / 2 s / 5 s / 10 s / 30 s / pause). localStorage persists the user's interval preference. Works without JS at degraded fidelity (page-level F5 manual refresh).
- Bundled CSS + JS via `include_str!` — zero external dependencies at runtime.
- `--storage-path` (or `[storage]` config block) required: server is store-mode only, exits with user error on missing/empty DB.
- Feature-gated under a new `web` Cargo feature on `agentprof-cli`, included in the existing `full` default feature.
- Test plan: per-route unit tests (`Router::oneshot`) + 5 e2e tests (real subprocess + reqwest) + HTML snapshot tests for the dashboard chrome.
- ADR-0024 codifies the rendering + live-refresh + storage-requirement decisions.

### Out of scope (deferred)

- **Authentication / authorization** — local-only single-user case has no auth need. Non-loopback bind logs a `tracing::warn!` recommending a reverse proxy. If a real need emerges, M2.6 wave can add bearer + TLS in a mode parallel to M2.4 OTLP hardening.
- **Multi-user / team dashboards** — out of scope; conflicts with single-user-laptop primary use case.
- **WebSocket / Server-Sent Events / sub-second latency** — polling at 1 s is responsive enough; complexity not justified for the use case.
- **JavaScript framework** (React / Vue / htmx / Alpine) — vanilla JS is enough for the swap-innerHTML pattern; framework adds build-tooling complexity inconsistent with the project's Rust-only ethos.
- **Static-file generator mode** — separately implementable on top of `analyze --export html` if needed; not part of this wave.
- **Embed flamegraph as interactive SVG** — current `analyze --export html` already renders a static SVG flamegraph; web dashboard reuses that asset as-is. Interactive zoom/filter is a follow-up wave.
- **`watch`-style cross-session live aggregate over time** — covered by `/aggregate?since=<dur>` with polling; explicit "time-series" view is out of scope.
- **Multi-tab session comparison** — too speculative; browser tabs achieve it manually.
- **Server emits OTLP itself** (i.e. "agentprof serve" being an OTLP receiver too) — separate concern; users run `agentprof ingest-otlp` + `agentprof serve` independently and they share the SQLite store.

## 3. Design decisions

### D-1: Reuse existing axum + askama infrastructure

The OTLP receiver (M2.2) already pulls `axum`, `tower`, `tonic`, `tokio` into the build when the `otlp` feature is on. Adding the dashboard reuses this stack rather than introducing a different HTTP library.

`askama` is already used by `format::html` (single-session report) and `format::aggregate_html` (aggregate report). New dashboard templates extend the same family.

**Rationale**: zero new top-level workspace deps for this wave (only feature-flag additions). Maintainers know these libraries.

**Alternatives considered:**

- **`warp` / `actix-web` / `rocket`** — switching frameworks fragments the project's HTTP knowledge for no benefit.
- **Bare `hyper` + manual routing** — re-invents axum's route DSL.

### D-2: Vanilla JS poller (no framework)

Live refresh uses ~80 lines of vanilla JavaScript wrapping `setInterval` + `fetch` + DOM swap. Bundled inline via `include_str!`; no build step, no `npm`, no transpilation.

**Rationale**: the polling pattern is trivial; a framework would add a build pipeline disproportionate to the JS surface. Matches the project's "no JS framework" precedent (existing HTML reports embed CSS but no JS).

**Alternatives considered:**

- **`htmx`** — close fit for "swap HTML chunks on poll" pattern. Adds one external script dependency (~14 KB) which we'd bundle. Reasonable; declined to minimize external surface, but a future maintainer can swap to htmx in one PR if the vanilla JS grows beyond ~150 LOC.
- **React / Vue / Svelte / Alpine** — require build tooling (Vite / esbuild / etc.) and runtime VM. Disproportionate.
- **WebSocket / SSE** — sub-second latency unjustified per Q-2.

### D-3: HTML-chunk endpoint pattern (not JSON API)

For each dynamic view, the server exposes **two** endpoints:

- `GET /<view>` → returns full HTML page (dashboard chrome + main content)
- `GET /api/<view>.html` → returns ONLY the `<main>` content fragment

JS poller calls the `/api/*.html` endpoint and replaces `document.getElementById('main').innerHTML`. No JSON parsing on the client; the server reuses the same render function for both endpoints (single page is `<chrome> + render() + </chrome>`; api endpoint is just `render()`).

**Rationale**: zero JSON serialization/deserialization on the client. Server already has the HTML render code (askama templates). htmx-style without htmx.

**Alternatives considered:**

- **JSON API + client-side DOM building** — requires a JS templating system or hand-rolled `document.createElement` calls. More code, more bugs.
- **Full-page reload via meta-refresh** — loses scroll position + form state; flickers.

### D-4: Single SQLite read per request (no caching layer)

Every HTTP request hits the SQLite store directly via the existing `SessionDataSource` trait (M2.1). No in-memory cache layer, no result memoization.

**Rationale**: M2.1 SQLite reads are fast (<5 ms for typical queries on session counts in the 100s); a poll every 5 s is well within budget. Adding a cache would introduce staleness bugs and invalidation complexity for marginal latency gain.

**Alternatives considered:**

- **In-memory LRU keyed on query params** — saves 1-2 ms per repeat poll. Not worth the complexity at single-user scale.
- **Long-lived in-process state synced from SQLite** — same trade-off plus stale-data risk if external writers (CLI / OTLP receiver) mutate the store.

### D-5: Server requires store mode (no adapter scan fallback)

`agentprof serve` exits with `ExitKind::UserError` if `--storage-path` is missing or the store is empty/uninitialized. Users must run `agentprof db init` + `agentprof db ingest` (or `agentprof ingest-otlp`) first.

**Rationale**: the live-refresh pattern is incompatible with adapter scans (which can take seconds for large session directories). Forcing the store-mode dependency makes performance predictable. Users already have `analyze --export html` for ad-hoc no-store report generation.

**Alternatives considered:**

- **Adapter fallback (option B from brainstorm Q-4)** — degrades responsiveness; mixes two data paths in one server.
- **Auto-bootstrap (run ingest then serve)** — surprising side effects; user better off doing it explicitly.

### D-6: Default port `4329`, loopback only, no auth

Default bind is `127.0.0.1:4329` (port chosen close enough to OTLP's `4317`/`4318` to be recognizable as agentprof, distinct enough to not collide). `--bind 0.0.0.0:N` allowed but logs a `tracing::warn!` recommending a reverse proxy for any non-loopback deployment. No bearer / TLS in this wave.

**Rationale**: the primary use case (Q-1: "live monitoring while using agent") is single-user-local. Auth complexity for a localhost dashboard is over-engineering. Future hardening can mirror M2.4 OTLP if non-loopback usage materializes.

**Alternatives considered:**

- **Always require bearer token, even for loopback** — friction without benefit; users can `curl` localhost without auth in any other dev tool.
- **Bind to a Unix socket by default** — better isolation but breaks the "open browser to URL" muscle memory.

### D-7: Release as v0.3.3 (not v0.4.0)

`agentprof serve` is a substantial new feature (new subcommand, new public API surface, new templates, new tests) that would normally justify a SemVer minor bump. However, the post-v0.3.1 numbering decision reserves **v0.4.0 for the Phase 3 multi-agent milestone** (Claude + Codex adapters). M2.3 ships as **v0.3.3** to preserve that reservation, matching the precedent set by M2.5 cache analytics (which also added public API but shipped as v0.3.1).

**Rationale**: in pre-1.0 territory, SemVer is loose enough that "feature shipped" doesn't dictate the major-vs-minor distinction; the project narrative does. Documented in CHANGELOG `[0.3.3]` preamble.

## 4. API additions

### 4.1 New CLI subcommand: `agentprof serve`

```
agentprof serve [OPTIONS]

OPTIONS:
  --bind <ADDR>            Bind address. Default 127.0.0.1:4329.
                           Non-loopback bind logs a warning.
  --storage-path <PATH>    SQLite store path (overrides config-file).
  --interval-default <S>   Default browser-side poll interval in seconds.
                           Default 5. Range 1..=60.
  --no-open                Skip the default "open browser on start" behavior.
  --quiet                  Suppress per-request tracing output.
```

`--storage-path` resolution: CLI flag > env (`AGENTPROF_STORAGE_PATH`) > config-file `[storage] path` > default XDG path (matches M2.1 behavior).

Exit codes (per `docs/architecture.md` §8.1):
- `0` graceful shutdown (SIGINT / SIGTERM)
- `1` user error (bad flag, missing store, port in use)
- `2` data error (corrupt SQLite, schema mismatch)
- `3` output / I/O error (bind fail, OS resource exhausted)

### 4.2 New `[serve]` config-file block (optional)

```toml
[serve]
bind             = "127.0.0.1:4329"
interval_default = 5
auto_open        = true   # spawn browser to URL on start; --no-open overrides
```

CLI > env > config-file > built-in defaults (mirrors `[otlp]` block from M2.2 T8.2).

### 4.3 No new core API

Web dashboard is a render layer on top of existing public surfaces:
- `agentprof_storage::SqliteDataSource` (M2.1)
- `agentprof_storage::Db::open` (M2.1)
- All `format::*` modules (M1.x / M2.5)

Nothing new exposed in `agentprof-core` / `agentprof-storage` / `agentprof-adapters` / `agentprof-tui`.

## 5. Implementation outline

### 5.1 New module structure

```
crates/agentprof-cli/
  src/cmd/serve/
    mod.rs            ← clap struct + run_async entry + signal handling
    router.rs         ← axum Router construction
    handlers.rs       ← per-route handler fns
    static_assets.rs  ← include_str! bundling
  templates/dashboard/
    layout.html       ← top nav + main + footer chrome
    sessions.html     ← sessions list
    session.html      ← single session detail
    aggregate.html    ← cross-session aggregate
    mcp_waste_servers.html
    mcp_waste_detail.html
    chunks/           ← /api/*.html endpoints (main-panel-only fragments)
      sessions.html
      session.html
      aggregate.html
      mcp_waste_servers.html
      mcp_waste_detail.html
  templates/dashboard/static/
    dashboard.css     ← unified styling (reuses existing report.html CSS classes where possible)
    dashboard.js      ← ~80 LOC vanilla polling + toolbar
    favicon.svg       ← tiny inline SVG favicon
```

### 5.2 Reuse layer

For each web view, the underlying data + format helpers come from existing code:

| View | Reused render fn | Adaptation |
|---|---|---|
| Sessions list | `cmd::list::format_table` returns plain text — extract a `ListRow` → HTML row helper into `format::list_html` (new tiny module) | New |
| Single session | `format::html::build_cache_section` etc. — extract sections from the existing `report.html` template into reusable askama partials | Refactor |
| Aggregate | `format::aggregate_html::render` — already produces HTML; embed inside dashboard chrome | Trivial |
| MCP-waste | `cmd::mcp_waste` — already supports `--export html`; embed | Trivial |

Strategy: minimal `pub(crate)` extractions in `format/*` modules so the dashboard handlers can call the same render code without copy-paste. ADR-0024 codifies the "extract before duplicate" rule.

### 5.3 Live refresh JS (sketch)

```javascript
// Bundled inline at /static/dashboard.js
(function() {
  const main = document.getElementById('main');
  const status = document.getElementById('refresh-status');
  let intervalSec = parseInt(localStorage.getItem('agentprof.interval') || '5', 10);
  let paused = false;
  let timer = null;

  async function refresh() {
    if (paused) return;
    const url = new URL(window.location.pathname.replace(/^\//, '/api/') + '.html',
                       window.location.origin);
    url.search = window.location.search;
    try {
      const r = await fetch(url, { headers: { 'Accept': 'text/html' } });
      if (r.ok) {
        main.innerHTML = await r.text();
        status.textContent = 'updated ' + new Date().toLocaleTimeString();
      } else {
        status.textContent = 'refresh failed: ' + r.status;
      }
    } catch (e) {
      status.textContent = 'refresh error: ' + e.message;
    }
  }

  function applyInterval() {
    if (timer) clearInterval(timer);
    if (intervalSec > 0 && !paused) {
      timer = setInterval(refresh, intervalSec * 1000);
    }
  }

  // Pause button + interval picker wiring (~20 LOC each, omitted from sketch)
  // ...

  applyInterval();
})();
```

### 5.5 Bind warning + observability

- Loopback bind: `tracing::info!(addr = %addr, "agentprof serve listening")`
- Non-loopback bind: `tracing::warn!(addr = %addr, "agentprof serve listening on non-loopback — recommend reverse proxy for auth")` before binding
- Per-request: `tracing::debug!(method = %req.method(), path = %req.uri().path(), status = %resp.status())` (low volume, debug-level only)
- Health probe (`/healthz`): no tracing (would spam logs under load-balancer health checks)

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Vanilla JS grows beyond 80 LOC over time | When it crosses ~150 LOC, switch to htmx (one PR; same swap-HTML pattern); ADR-0024 footnotes this as the escape hatch |
| Auth-less dashboard exposed accidentally on LAN | Default 127.0.0.1; non-loopback bind logs explicit warning; README documents reverse-proxy pattern |
| Browser caches stale HTML chunks across polls | Server emits `Cache-Control: no-store` on all dynamic endpoints |
| SQLite concurrent writes during reads | Already handled — M2.1 store uses WAL mode (rusqlite default), readers don't block writers and vice versa |
| Polling load on the SQLite store under aggressive interval (1s) | Default 5s; 1s minimum is a user choice; per-request query is <5ms so even 1s polling is negligible |
| Browser leaves the tab open for hours; localStorage interval grows unbounded | Bounded by the interval picker (max 30s); pause is a valid setting |
| User binds to 0.0.0.0 by accident on a shared machine | Warn at startup; document; consider future hardening (M2.6) if it becomes a recurring issue |
| Spec creep into "real-time push" — someone wants SSE later | Add as future wave; current pattern is fine; ADR-0024 D-3 explicitly bounds scope |
