# M1.7 — v0.1.0 release strategy & infrastructure

**Date**: 2026-06-06
**Topic ID**: `m1.7-release`
**Pipeline stage**: brainstorming → spec → ADR-0014 → implementation
**Backlog items**:
- `m17-bs-*` (7 subtodos, the brainstorm process itself)
- `full-review-workspace-2-release-yml-stub` (hard blocker: wire cargo-dist)
- `full-review-workspace-3-actions-sha-pin` (hard blocker: SHA-pin GHA)

> **TL;DR** — Wire `cargo-dist` into the current stub `.github/workflows/release.yml`
> so that pushing tag `v0.1.0` to a fresh `github.com/agentprof/agentprof` repo
> automatically builds 4-platform binaries (Linux x86_64/aarch64,
> macOS x86_64/aarch64) and publishes a GitHub Release with a one-line
> shell installer. **No crates.io publish** for v0.1.0 (decision Q1 / D-1).
> SHA-pin all `uses:` action references in CI workflows (rolling
> `@stable` / `@master` refs intentionally exempt). Rewrite README install
> section to point at the installer URL. CHANGELOG follows the standard
> Keep-a-Changelog `[Unreleased]` → `[0.1.0] - YYYY-MM-DD` cutover at tag
> time. Two-stage release: local prep (commits 1–10) → tag-push trigger
> (commit 11) with abort criteria if any Stage-2 gate fails.

---

## 1. Context

`agentprof` has 23 commits of feature work landed locally (F1.x / F2 /
B1 / C1–C2 / D1–D3 / B1 / etc.), 809 passing tests, and `Cargo.toml`
already set to `version = "0.1.0"`. What's missing is **the act of
publishing it as a tagged release** that anyone can install.

Two things stand in the way today:

1. **Hard blocker** `full-review-workspace-2-release-yml-stub`:
   `.github/workflows/release.yml` is a stub that only creates an empty
   draft release. `README.md` already advertises `cargo install agentprof`
   via cargo-dist, but the workflow has never been wired up. Either ship
   the workflow or retract the README promise.
2. **Hard blocker** `full-review-workspace-3-actions-sha-pin`: every
   `uses: org/repo@vX` in `ci.yml` / `nightly-msrv.yml` / `release.yml`
   is tag-pinned, not SHA-pinned. OpenSSF Scorecard considers this a
   medium-severity supply-chain risk (malicious upstream could re-tag
   `v4` to a compromised commit).

There's also an unrelated 0-bus-factor practical: **there is no GitHub
repo yet** (`git remote -v` is empty — pure local repo). M1.7 is
where the project moves from "private local checkout" to "publicly
installable artifact." That step has more decisions than just CI:
crates.io publish-or-not, supported platforms, signing, MSRV
commitment, install instructions, CHANGELOG cutover.

This spec answers all of them.

## 2. Decisions (Q1 – Q10 + cargo-dist-init choice; codified in ADR-0014)

| ID | Decision | Q | Rationale |
|---|---|---|---|
| **D-1** | **No crates.io publish** for v0.1.0 | Q1 → user revised | YAGNI for first release; the lib API surface is large and pre-stable; can open later without breaking anything. |
| **D-2** | GitHub repo = **`github.com/agentprof/agentprof`** | Q2 | Matches `Cargo.toml` `repository` / `homepage` (already set during M1.0). User creates repo via `gh repo create` / web UI; spec assumes the slug. |
| **D-3** | 4 lib crates set `publish = false`; cli omits the field | (derived from Q1+Q3) | Defence — even if crates.io publish is opened later, the lib crates aren't accidentally published from a stray `cargo publish`. CLI omits the field to leave the door open. |
| **D-4** | **Primary install** = one-line installer script | Q4 | `curl -fsSL .../releases/latest/download/agentprof-cli-installer.sh \| sh`. cargo-dist generates this for free; no Rust toolchain required for end users. |
| **D-5** | Build matrix = **4 platforms**: linux x86_64 / linux aarch64 / macOS x86_64 / macOS aarch64 | Q5 | cargo-dist default recommendation; covers ≥95% of developer audience. **Windows excluded** for v0.1.0 — TUI testing matrix would balloon; defer to v0.2+ if demand surfaces. |
| **D-6** | **SHA-pin** all immutable-tag actions; **rolling refs** (`@stable` / `@master`) intentionally remain tag-pinned with a comment | Q6 + §4 | Supply chain hardening (`@v4` could be re-tagged maliciously); rolling refs are the design (we WANT each CI run to pick up the current stable Rust). Dependabot watches both and bumps SHA + comment together. |
| **D-7** | **No signing** — neither tag nor binary | Q7 | cargo-dist generates SHA-256 checksums for downloads, sufficient for integrity verification. GPG key management + GH secrets exceeds v0.1.0 scope. Can add minisign / sigstore in a later release if attestation becomes a user ask. |
| **D-8** | First public version = **`v0.1.0`** | Q8 | Matches existing `Cargo.toml`. SemVer 0.x signals "API not stable" which is honest for this project's current state (e.g. C1 BREAKING JSON-since-sentinel landed in the last week). |
| **D-9** | CHANGELOG follows **Keep-a-Changelog standard cutover** | Q9 | `## [Unreleased]` body becomes `## [0.1.0] - YYYY-MM-DD`; new empty `## [Unreleased]` added above. Single `chore(release): v0.1.0` commit. Link refs at bottom: `[0.1.0]: .../releases/tag/v0.1.0`. |
| **D-10** | **Two-stage release**: local prep commits → tag push triggers CI; any Stage-2 failure aborts the whole release | Q10 | Simpler than rc.1 pipeline; if cargo-dist build fails mid-way, just delete tag + release and reroll. Doesn't pre-publish a broken release. |
| **D-11** | `cargo dist init` generates yml + **manual one-time SHA-pin** afterward; no xtask automation | release.yml-init choice A | YAGNI. cargo-dist upgrades are infrequent; re-running `cargo dist generate-ci github` + re-SHA-pin manually is acceptable churn given the alternative (30-line `xtask sha-pin-release-yml` tool we'd have to maintain). |

## 3. Architecture

M1.7 is **infrastructure work**, not feature work. The deliverable is
"running `git push origin main --tags` triggers a GitHub Actions pipeline
that builds 4-platform binaries and publishes a GitHub Release." The
deliverable is also "anyone can `curl | sh` the result."

```
                                            ┌─ Linux x86_64
   git push --tags                          ├─ Linux aarch64
        │                                   ├─ macOS x86_64
        ▼                                   └─ macOS aarch64
  .github/workflows/release.yml (SHA-pinned)│
        │                                   ▼
        ├── plan job: cargo dist plan ────→ tarball / installer.sh per platform
        ├── build job × 4 platforms:                                     │
        │     cargo dist build --target=<triple>                         │
        ├── upload job: gh release upload <files> + SHA256SUMS           │
        └── (NO crates.io publish step — D-1)                            │
                                                                         ▼
                                            GitHub Release v0.1.0 page
                                                            │
                                                            ▼
            User runs:
            curl -fsSL https://github.com/agentprof/agentprof/releases/latest/download/agentprof-cli-installer.sh | sh
            → ~/.cargo/bin/agentprof
```

**File touch surface** (10 file groups):

| # | File | Change |
|---|---|---|
| 1 | `.github/workflows/release.yml` | Replace stub with cargo-dist-generated content + SHA-pin |
| 2 | `dist-workspace.toml` (new) | cargo-dist config; 4 targets, shell installer, no publish jobs |
| 3 | `Cargo.toml` (workspace + 4 lib crates) | `[workspace.metadata.dist]` segment + `publish = false` on 4 lib crates |
| 4 | `README.md` | Install section rewrite (Section 5 of this spec) |
| 5 | `.github/workflows/ci.yml` | SHA-pin 9 `uses:` references (rolling refs exempt with comment) |
| 6 | `.github/workflows/nightly-msrv.yml` | SHA-pin 3 `uses:` references (rolling ref exempt) |
| 7 | `.github/dependabot.yml` (new) | github-actions ecosystem, weekly cadence |
| 8 | `CHANGELOG.md` | Tag-time `[Unreleased]` → `[0.1.0] - DATE` cutover + link refs |
| 9 | `docs/architecture.md` + `docs/plan.md` + `CONTRIBUTING.md` | Sync L1 — release process documented |
| 10 | `docs/internals/adr-0014-v0.1.0-release-strategy.md` (new) | Codifies D-1 through D-11 |

## 4. Component: cargo-dist setup (`dist-workspace.toml` + new `release.yml`)

### 4.1 cargo-dist install + init (one-time)

```sh
# 1. Install cargo-dist locally (dev tool — not a runtime dep).
#    Pin to a minor version to avoid surprise major bumps.
cargo install cargo-dist --version "^0.21"

# 2. Interactive init — answers we'll give:
cargo dist init
#   installer:      shell
#   targets:        x86_64-unknown-linux-gnu, aarch64-unknown-linux-gnu,
#                   x86_64-apple-darwin, aarch64-apple-darwin
#   ci:             github
#   publish-jobs:   (none) ← critical, leaves D-1 satisfied
#   install-path:   ~/.cargo/bin

# 3. Generate release.yml replacing the stub.
cargo dist generate-ci github

# 4. Manual SHA-pin pass on the new release.yml (D-6).
# 5. Local validation:
cargo dist plan    # validates config + lists artefacts; doesn't build
```

### 4.2 Expected `dist-workspace.toml` content

Generated by `cargo dist init`; we'll commit it verbatim and add the
note below as a comment header:

```toml
# cargo-dist configuration. Edit via `cargo dist init` rather than by
# hand — running `cargo dist generate-ci github` regenerates
# `.github/workflows/release.yml` based on this file. Per ADR-0014
# D-11, after regen we manually re-SHA-pin the new release.yml.

[dist]
# Lock minor version to match the `cargo install --version "^0.21"`
# command in CONTRIBUTING.md "Release process" section.
cargo-dist-version = "0.21.X"        # X = actual patch at init time
ci = ["github"]
installers = ["shell"]
targets = [
    "x86_64-unknown-linux-gnu",
    "aarch64-unknown-linux-gnu",
    "x86_64-apple-darwin",
    "aarch64-apple-darwin",
]
publish-jobs = []                    # D-1: no crates.io
```

### 4.3 `Cargo.toml` workspace metadata addition

```toml
# Append to root Cargo.toml:
[workspace.metadata.dist]
# (cargo-dist reads cargo-dist-version + targets from dist-workspace.toml;
# this section is intentionally minimal. Future per-crate dist overrides
# would land here as [package.metadata.dist] under each crate.)
```

### 4.4 `publish = false` on 4 lib crates

```toml
# In crates/agentprof-core/Cargo.toml (and -adapters, -storage, -tui):
[package]
name = "agentprof-core"
# ... existing fields ...
publish = false  # M1.7 D-3 — gated until lib API stabilises

# agentprof-cli intentionally OMITS `publish` to leave crates.io open.
```

### 5.3 Excluded install paths (explicit YAGNI)

- ❌ **Homebrew tap** — cargo-dist 0.21 supports it, but requires a separate
  `agentprof/homebrew-tap` repo with its own formula maintenance. Defer
  to user demand.
- ❌ **Windows MSI** — D-5 excludes Windows from the build matrix.
- ❌ **Docker image** — v0.1.0 target audience is command-line developers
  using `cargo install`, not ops engineers needing a container image.
- ❌ **crates.io `cargo install agentprof`** — D-1.

## 6. Component: GHA SHA-pin pass

### 6.1 Five action references to pin

`grep -rE "uses: " .github/workflows/` audit (run at spec time):

| Action | Used in | Pin strategy |
|---|---|---|
| `actions/checkout@v4` | ci.yml ×4 + nightly.yml ×1 + release.yml ×1 | **SHA-pin** |
| `dtolnay/rust-toolchain@stable` | ci.yml ×3 | **NOT pinned** (rolling) |
| `dtolnay/rust-toolchain@master` | ci.yml ×1 + nightly.yml ×1 | **NOT pinned** (rolling) |
| `Swatinem/rust-cache@v2` | ci.yml ×3 + nightly.yml ×1 | **SHA-pin** |
| `EmbarkStudios/cargo-deny-action@v2` | ci.yml ×1 | **SHA-pin** |
| `softprops/action-gh-release@v2` | release.yml ×1 (stub — will be replaced) | (deal with after Section 4) |

### 6.2 SHA lookup workflow

```sh
# For an immutable tag:
gh api repos/actions/checkout/git/refs/tags/v4.2.2 --jq '.object.sha'

# For a rolling ref (just to record current value as comment, not pin):
gh api repos/dtolnay/rust-toolchain/commits/stable --jq '.sha' | head -c8
```

### 6.3 Pin format

```yaml
# Before:
- uses: actions/checkout@v4
# After:
- uses: actions/checkout@<40-char-sha>  # v4.2.2

# Rolling ref — keep tag-pin, document intent:
- uses: dtolnay/rust-toolchain@stable
  # ^ Rolling ref intentionally NOT SHA-pinned (we want each CI run
  # to pick up the current stable Rust toolchain). See ADR-0014 D-6.
```

### 6.4 New release.yml SHA-pin pass

`cargo dist generate-ci github` will write a fresh `release.yml` referencing
whatever actions cargo-dist 0.21.x uses (typically `actions/checkout`,
`actions/upload-artifact`, `actions/download-artifact`,
`softprops/action-gh-release`). All immutable tags get the same SHA-pin
treatment as §6.3 immediately after the regen.

### 6.5 Dependabot

```yaml
# .github/dependabot.yml (NEW)
version: 2
updates:
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
    # Dependabot auto-bumps SHA AND updates the `# vX.Y.Z` comment in
    # one PR — no separate comment-sync step needed.
```

## Release process (maintainers only)

The release is two-stage. Stage 1 happens entirely locally; Stage 2 is
triggered by pushing the tag.

### Stage 1 — Local prep

1. Update `CHANGELOG.md`: move `[Unreleased]` body into a new
   `[X.Y.Z] - YYYY-MM-DD` section; leave an empty `[Unreleased]` above.
   Add the link reference at the bottom.
2. Bump `Cargo.toml` `[workspace.package].version` to `X.Y.Z`.
3. Run the full local gate: `cargo fmt --all --check && cargo clippy
   --workspace --all-targets --all-features -- -D warnings &&
   cargo test --workspace --all-features && RUSTDOCFLAGS="-Dwarnings"
   cargo doc --no-deps --workspace && cargo dist plan`.
4. Commit: `chore(release): vX.Y.Z`.

### Stage 2 — Tag push

5. `git tag vX.Y.Z`
6. `git push origin main --tags`
7. Watch the Actions tab: `release.yml` should run plan → build × 4
   platforms → upload to GitHub Release.
8. Verify the GitHub Release page has 4 platform tarballs + installer.sh
   + SHA256SUMS.
9. Test the installer: `curl -fsSL <installer-url> | sh` from a clean
   shell and run `agentprof --version` — expect `X.Y.Z`.

### If any Stage-2 step fails

```sh
git push --delete origin vX.Y.Z
git tag -d vX.Y.Z
gh release delete vX.Y.Z
```
Fix the issue, return to Stage 1 step 4 (re-commit with the fix) and re-tag.

### Updating cargo-dist

When a new cargo-dist minor lands:
```sh
cargo install cargo-dist --version "^0.NEW"
cargo dist init   # re-confirm same answers
cargo dist generate-ci github   # regenerates release.yml
# Manually re-SHA-pin the new release.yml (ADR-0014 D-11) before commit.
```
```

## 9. Commits (per §5.7 granularity)

11 commits total. **Commits 1–10 are pure local work** — they can land
on the existing local-only `main` branch without GitHub repo existing
yet. **Commit 11** is the trigger commit, executed only after the user
creates the GitHub repo + pushes the first 10 commits.

```
1.  docs(spec):    M1.7 v0.1.0 release strategy design          [this file]
2.  docs(adr):     ADR-0014 — release decisions
3.  docs(plan):    M1.7 v0.1.0 release implementation plan

# Pure-local prep (independent of GH repo existence):
4.  chore(workspace): mark 4 lib crates publish=false
5.  ci:            SHA-pin actions in ci.yml + nightly-msrv.yml
6.  ci:            add .github/dependabot.yml for actions ecosystem

# Cargo-dist wire-up (user must have run `cargo dist init` locally):
7.  ci(release):   wire cargo-dist via `cargo dist init` (replaces stub)
8.  ci(release):   SHA-pin actions in new release.yml

# Docs sync:
9.  docs(readme):  rewrite Install section for v0.1.0 release
10. docs(arch/plan/contributing): sync L1 docs for release process

# Trigger commit (Stage 2 begins after this):
11. chore(release): v0.1.0 — CHANGELOG cutover + tag
```

Why split commits 5 / 6 / 7 / 8 instead of one "ci hardening" commit:
each is independently reviewable and revertible. Commit 5 doesn't depend
on cargo-dist; commit 7 depends on the user running `cargo dist init`
locally and producing files; commit 8 depends on 7's diff being on disk.

## 10. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `cargo dist init` generates a release.yml that differs significantly from spec assumption (e.g. uses different actions, different job structure) | Medium | Low | We commit verbatim what `cargo dist init` writes; SHA-pin pass adapts to whatever actions appear. The spec's §6.4 doesn't predetermine the action list. |
| GitHub repo slug `agentprof/agentprof` is taken | Medium | High | User confirms repo name during Stage 2 step 5 (before tag push). If taken, fall back to `agentprof/agentprof-cli` (matches the bin name); update `Cargo.toml` `repository` + `homepage` + README URLs + ADR-0014 D-2 + spec §2 D-2 in a follow-up commit BEFORE pushing the tag. |
| cargo-dist release builds time out or fail on aarch64-darwin (Apple Silicon cross-compile is slow on x86 runners) | Medium | Medium | cargo-dist uses native Apple Silicon runners as of 0.21+; verify during Stage 1 step 3 `cargo dist plan`. Stage-2 abort path handles a partial fail. |
| Installer.sh chmod / PATH issues on user's machine | Low | Medium | cargo-dist's installer.sh is well-tested upstream. Stage 2 step 9 includes a real-world install verification; if it fails, abort. |
| Some `[Unreleased]` entry refers to a future feature not actually shipped | Low | High (release lies) | Spec §7 cutover is a manual diff review — Stage 1 step 1 includes "read every `[Unreleased]` bullet, confirm the commit it references actually exists in `git log --oneline`." |
| Tag `v0.1.0` is pushed but Stage-2 verification fails → release stays half-baked | Low | High | Abort path at end of §8.4 (delete tag, delete release, fix, reroll). Aggressively use this path; do not "patch forward" from a broken v0.1.0. |
| User runs `cargo dist init` with wrong answers (e.g. accidentally adds Windows or enables crates.io publish) | Low | Medium | Spec §4.1 enumerates the exact answers; user copy-pastes from this spec. Verify with `cat dist-workspace.toml` before commit 7. |

## 11. Out of scope (explicit YAGNI)

- **crates.io publish** (D-1, deferred until lib API stabilises)
- **Windows binaries** (D-5, deferred to v0.2 if user demand surfaces)
- **GPG / minisign / sigstore signing** (D-7, deferred)
- **Homebrew tap, MSI, Docker image** (§5.3)
- **GitHub release notes auto-generation from PRs** (CHANGELOG is the
  source of truth; auto-generation creates a second-source-of-truth
  problem per Q9-B's rejection)
- **Branch protection / signed commits / required reviews on the GH repo**
  (account-level setup, owned by the user not this spec)
- **CI / release status badges on README** (premature; one CI run isn't
  meaningful UX yet)
- **xtask sha-pin-release-yml automation** (D-11 explicit YAGNI)
- **MSRV bump policy / minimum supported Rust version statement in README**
  (`Cargo.toml` already says `rust-version = "1.78"`, README §"From source"
  mentions it; full policy doc deferred)
